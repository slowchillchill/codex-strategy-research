# 共同研究流程

## 1. 研究对象与权威来源

研究的目标是判断策略能否在真实业务约束下创造可采用的经营价值。代码正确、训练完成、回测盈利和正式采用是不同结论。

先核对用户当前请求、目标仓库 `AGENTS.md`、所属研究任务的当前正文及适用折叠合同、相关最新决定。研究方法不能修改业务合同。已有实现、旧测试和旧决定仍要对照实际业务检验；发现冲突时说明事实、影响与替代方案，不能暗改语义。

当前项目合同入口统一在此维护：[总体合同 #1](https://github.com/slowchillchill/btc-updown-marketmaker/issues/1)、[A 合同 #185](https://github.com/slowchillchill/btc-updown-marketmaker/issues/185)、[A 研究 #315](https://github.com/slowchillchill/btc-updown-marketmaker/issues/315)、[B 合同 #181](https://github.com/slowchillchill/btc-updown-marketmaker/issues/181)及[裁决索引 #62](https://github.com/slowchillchill/btc-updown-marketmaker/issues/62)。所属研究任务以当前签发为准；只读取实际依赖，不把其他路线的全部未完成事项变成当前研究前置。正文与折叠内容同样有效，摘要不能替代合同。

通用工程原则仍从目标仓库指定的个人规则入口读取。研究主会话和子角色均不能自行启用开发治理、切换为开发身份或派生开发代理。发现工程问题按[工程交接](engineering-handoff.md)向用户汇报，由用户审查后另行签发开发组。

### 仓库、产物与平台记录的权限

| 对象 | 研究权限 |
| --- | --- |
| 业务仓库的源码、脚本、配置、文档及 `AGENTS.md` | 只读，可核对实现、合同与历史；不编辑、修复或清理 |
| 业务仓库的 Git 与 PR | 不创建研究开发分支或可写任务工作树，不提交、推送、开 PR、提交正式 Review、合并、重置或切换他人的工作树 |
| 明确分配的仓库外研究目录 | 可写完整实验配置、调用已交付入口的包装脚本、派生分析、报告、日志、成本记录和训练生成的权重 |
| 所属研究 Issue 与 Projects | 仅研究主会话在当前任务授权内维护，按第七节记录；平台元数据可写不等于 Git 内容可写 |

现有能力支持的参数与选项可在批准范围内研究。仓库外脚本只组织现有入口或分析原始事实，不通过临时副本、补丁、插件、动态替换或“原型”另行实现策略、特征、奖励、模型组件、训练算法、撮合或账本。研究辅助分析错误可在其授权目录内更正并保留替代关系；业务仓库中的同类错误也须交用户审查。

优先复用已交付产物。确需构建不变源码时，须在当前准备授权与预算内，用现有能力把构建、缓存和输出定向到仓库外，并确认不会改写源码、锁文件或其他仓库内容；不能做到时报告入口缺口。原始数据和旧证据保持原身份，不就地改写。研究调用不授权修改知识库、研究 Skill 或其他规则仓库；规则维护须有单独任务授权。

## 2. 以研究问题组织一轮工作

先说清要决定什么，再安排计算。问题应能被证据推翻，例如“主动补腿是否降低库存代价，代价是否超过其实际费用”，而不是“多跑几个窗口”。区分现有事实、假设与未批准建议。

在所属研究 Issue 中形成足以执行的研究约定；详细材料放在仓库外并从 Issue 引用，不新建重复状态系统。至少讲清：

- 业务问题、机制假设、相反解释；结果将支持什么决定。
- 允许改变的候选范围、固定条件、对照、窗口、账户与数据用途；哪些改变需要重新批准。
- 执行环境及实际可用硬件、计算与并行安排、预算覆盖范围和上限、成本估计依据、进度与停止办法，按第五节落实。
- 观察指标、证据来源、完成判据，以及结论不能证明什么；产物位置、预计存储峰值、必要保留内容与清理责任，按第七节落实。

用户批准的是这一轮问题、范围与总预算。范围内的小实验、资源安排、分析和普通准备直接完成，研究者按信息价值与成本调整先后次序，不逐个参数申请许可。已明确的授权在同一轮交接后继续有效；旧轮次、旧检查点或其他路线的预算不能移用。

范围尚未批准时，可完成已有授权内的事实核对和可审查提案；运行授权不足的部分保持待批准。创建或安装本 skill 本身不是研究启动授权。

为形成假设、选择方法、寻找反证或核实外部事实，可以按当前问题自主检索互联网及项目知识库；先读[研究资料与方法借鉴](evidence-sources.md)。复用仍适用的阅读结果，不要求每轮机械搜索两边。资料检索属于本轮准备与分析成本；资料中的建议和代码不扩大执行授权。

## 3. 候选、输入与用途

一个结果必须能回到实际执行的候选。保留已交付源码提交、构建或模型产物身份、完整生效参数、规则与费用快照、Maker/Gamma 等采用政策、初始化、账户、窗口和随机条件。发现别人留下的未提交差异时如实披露其影响，不修改、不隐含纳入获准候选；使用哪个版本从实际交付和当前授权确定。只改候选名称不能产生新版本证据。参数默认值也要进入生效配置；不用一串命令代替其实际值。

先复用仍适用的输入审计，再补本轮窗口的真实缺口。manifest 闭合、文件存在或 gaps 为空不能单独证明业务完整；错误原因的数量也不能当作测出的断档数量。按实际问题核对身份、时间、盘口、规则和必要前史，避免为一个开发实验全池重扫。

在现有记录中维护实际历史用途：开发、候选验证、独立留出、必要初始化，以及谁查看了什么结果。批准某日期可用，不证明它独立、完整或初始化合法。A/B 分别核对用途授权；路线之间共享数据和研究发现也可能影响独立性。

只用训练或开发数据拟合参数与转换；验证结果若反过来改变候选或方法，记录其开发用途。最终留出在查看经营结果前冻结代码、完整候选、规则、初始化、模型选择及评价口径。不得先窥看留出收益来选窗口或决定是否报告。必要前史只承担入口要求的身份、规则或快照；额外预热、拟合或前日账户继承须有对应合同。

## 4. 实验设计与证据强度

先用成本较低且能区分解释的实验检验机制，再按实际信息缺口扩大。不能仅因排期写着“下一步全日”就推进。基线、对照与处理组使用可比输入、账户、时序、规则和随机条件；有差异时说明原因与可比范围。

一个实验可以改变多个因素，但要说明它回答的是组合效果，不能给单一因素归因。参数、日期、模型、检查点和分析口径的尝试都进入既有试验记录，包括失败、无效和未选中结果；不能只保留赢家。先定义主问题和关键证据，事后发现可以形成新假设，不能伪装成事前检验。

费用、未成交、库存、资金占用、结算和返佣按公共事实链解释。区分程序故障、正常交易拒绝、有效但负面的经营结果，以及无法确认的结果。优先复用请求、反馈、NOE、Ledger 和现有报告；证据缺口必须具体到一个问题和最小补充，不能借此启动泛化诊断工程。

报告效应大小、观察范围与不确定性。相关市场事件、重叠窗口和同一天内的成交不能自动当作独立样本。统计方法按数据依赖与问题选择，不强制某种检验、固定种子数或显著性门槛。短窗利润不能日化、年化或直接作为晋级依据；独立日账户不能拼成跨日复利净值。

## 5. 可执行预算、进度与停止

### 按当前硬件安排计算

防止大数据方案脱离实际环境、默认串行耗时，以及盲目增加并发反而降低吞吐。执行位置与资源边界遵守通用工程原则第六节“执行位置与计算资源”；以下要求落实到本轮研究约定，不另建资源账本。

- 设计大数据或长时间研究前，只读核对获准执行环境当前可用的 CPU 核数与配额、内存、GPU 与显存、输入输出所在文件系统的空间，以及影响吞吐的磁盘、网络和已有作业占用。区分机器总配置与本轮可用资源；启动前刷新影响方案的变化，交接已有事实仍适用时直接复用。核对正式入口的并行能力与限制，不能凭机器配置假定程序能够利用全部硬件。
- 按真实数据和状态依赖拆分独立候选、独立账户或输入分区，选择入口支持的多线程、多进程、批处理或 GPU 计算，充分使用获准资源。计划写明并发作业数、每作业线程与内存安排、GPU 分配及输入读取方式。连续账户、事件时序和训练状态保留必要顺序；单线程或较低并发须有依赖、入口限制或实测瓶颈依据，不能仅因代理步骤串行或默认配置就全程串行。
- 合计核算作业、内部线程池与数据加载的资源需求，避免嵌套并行、重复加载全量数据、内存换页或磁盘争用抵消收益。优先复用适用吞吐证据；确有缺口时，在当前运行授权及总预算内做代表性短测，比较有效吞吐、峰值内存或显存及端到端耗时，再确定并发与批量。没有短测授权时保留估计的不确定性，不把准备授权变成运行授权。
- 运行中结合实际进度与资源占用定位瓶颈，在既有接口、预算和业务语义内自主调整资源配置；不用固定利用率或固定线程数作为完成标准。增加数据范围、候选数量、改变训练批量等影响研究含义的调整仍按研究合同处理。需要新增并行能力或修改业务源码时按工程交接处理，不以资源优化绕过仓库只读边界。

### 预算与停止执行

执行前核对真实入口和已有运行证据。研究约定明确预算的单位与覆盖：准备和构建、输入处理、回放或训练、结果汇总、停止、证据归档、清理与返回分别计量；总预算与明确另计的部分不能混淆。按实际需要记录墙钟时间、CPU/GPU 时间、存储或付费资源，不另建监控平台。

保留候选数、窗口或训练工作量、并行单元及依赖、准确命令、输入和输出位置。时间估计包含实际读写与汇总成本，来自适用证据；未知就写未知。预算按本轮已消耗加新任务的预计成本核对，不能把每个子任务的预算分别视为总预算。并行任务还要核对合计资源占用及共同截止时间。

启动前验证现有停止能力：谁控制哪个作业、如何发出停止、是否停止派生进程、能否落盘、输出在中断后是否仍有效。优先核对实现和既有证据；缺少关键证据时提出最小短测，并将其计入获批范围。不能凭 `SIGTERM`、`timeout` 或检查点文件存在就承诺安全停止、完整结果或续跑。

用真实停止、汇总及必要归档清理的耗时安排返回预留，并在研究约定中写清软截止、最终截止及行为。预算到达后不启动新工作；已有工作按获批且验证过的停止办法处理，保留中断状态与可用证据。没有办法保证硬上限时，报告限制和可行预算方案，不能把建议时限宣称为可执行保证。强制终止是否允许、可能丢失什么结果，应在需要它的方案中说明。

记录实际开始、进度、累计成本和停止结果。长作业使用已有可控进度输出，按用户约定频率监督；总量或剩余时间不可靠时说明未知。失败、取消、超时和重试也消耗本轮预算。恢复能力按入口核验；重新开始和续跑是两件事。

## 6. 角色与审查

主会话负责研究问题、授权、成本、Issue／Projects 和最终汇报。它把有明确收益的有界工作交给研究角色，交接必须包括准确研究源路径及版本、只读业务源码与产物身份、研究 Issue、已批准范围和剩余预算、仓库外可写目录、输入输出、适用方法及资料绑定和返回要求。涉及计算或产物收尾时，一并交接可用资源、并行安排、保留用途与清理责任。角色无需自行猜测规则源或重新申请已有批准。

`research-designer` 只读提出假设、反例、资料依据与辨别实验；`experiment-runner` 仅在分配的仓库外目录承担批准范围内的配置、研究辅助脚本、执行和分析；`research-reviewer` 独立只读核对证据与方法适用性。每个共享写入路径指定一个负责人。子角色返回内容，不自行写 GitHub、派生开发角色或批准新范围。角色职责是协作约束，实际工具权限由 Codex 配置决定；不把它们宣称为安全隔离。

新的一轮存在实质设计取舍、进入更高证据阶段、最终留出或正式采用前，安排独立内容审查；范围内普通小实验复用适用审查，不要求机械派生三角色。审查必须判断实验能否回答问题、因果归因和比较是否成立、数据是否泄漏、资源安排与预算及停止能否执行，收尾方案是否保留复核结论所需证据，而不只数文件。阻塞意见指向当前要求与具体失败，不把审查偏好变成新合同。主会话核对依据，不以审查标签代替证据。

## 7. 记录、裁决与交付

研究 Issue 是当前研究约定与结论的权威入口，Projects 是规划和状态视图，仓库外材料提供详细证据。主会话统一维护三者的对应关系：

- Issue 正文维护当前进度、问题与任务、有效合同和完成条件、阻塞及下一项交付；批准内容与待批准建议分开。沿用通用工程原则的 Issue 呈现规则，更新原条目，不追加多份“当前状态”；适用折叠合同仍须完整读取。
- 评论记录方法依据与适用判断、实验方案和改变理由、运行回执、结果、成本、独立审查及交接。更正引用原记录并说明影响，不把事后假设伪装为事前检验。子角色的重要审查结论和限定条件如实保留。
- 必要的完整配置、脚本、模型和日志放在已授权的仓库外位置，记录内容身份和命令，保留范围按下文“研究产物收尾”确定。Issue 中保留可理解的结论和可供接手者使用的证据入口；本机路径与私有绑定经私有交接提供，不向公开记录泄漏，也不只贴无法访问的绝对路径。
- 沿用所属 Project 的已有字段和状态，在开工、审查、阻塞、恢复和交付等有意义变化后同步。卡片状态不能批准预算或替代用户签发；不自行建立第二套合同或字段体系。

已有研究 Issue 能承载本轮问题时继续使用；独立问题或独立签发范围才按项目规则建立关联研究任务，不为每个候选或运行建 Issue。父级只维护必要摘要及链接。研究问题得到可靠回答可以包括负面结果；完成本轮不表示策略采用，也不自动关闭仍有后续义务的父任务。

工程语义、接口或实质验收变化由用户裁决并通过获授权的工程流程维护原有裁决入口；研究侧关联原始决定。开工、预算签发、作业回执和普通实验结论留在所属任务，不自动成为工程裁决。

报告写清研究问题、实际候选与条件、全部相关尝试、行为和经营结果、实际成本、证据入口、局限及推荐下一步。区分“实验完成”“假设得到支持”“候选可正式采用”。盈利目标、晋级条件或投入尚未批准时，提出依据和选项，不编造数值门槛。

范围、总预算、数据用途、关键业务语义、评价口径、执行主机、资金风险或正式采用发生实质变化时，按当前合同停止受影响工作；存在更严格停止要求时遵守该要求。先核实事实并准备具体选项与推荐，再提交用户裁决。异常排查遵守个人工程原则；其中允许的修复不扩大本文件的仓库只读边界，也不借角色交接重置停止条件。PAPER/LIVE、部署、真实资金和服务器电源操作继续按各自授权处理。

研究记录引用采用的本仓库提交；未提交规则差异必须如实披露。更新方法后评估是否影响正在运行的轮次，保留旧运行身份与原始决定，不静默追认或改名。已有研究材料位于业务工作树时先保留现场；按明确交接范围复制到仓库外、核对内容与引用后使用，源工作树清理或代码交付由获授权维护者处理。业务项目的 Issues 和仓库外证据保留实验事实，本仓库只保留方法与验证其行为的小型合成案例。

### 研究产物收尾

防止研究已结束却长期保留全部中间产物，以及为了省空间只留结论、丢失反证和复核依据。通用工程原则第六节“构建产物与证据生命周期”同样适用于研究产物；路径、归属、共享使用、迁移核对、备份盘不可用的停止要求与释放空间口径沿用该节，不另建清理系统。

- 准备阶段在现有研究约定中说明输入、临时文件、缓存、检查点和结果的存放位置，估算并发作业的存储峰值及归档时的额外空间，指定保留用途和清理负责人。分批消费后已无用途的本轮中间产物及时清理，不等结论出来或磁盘写满；仍被作业、恢复、审查或后续已约定任务使用的对象继续保留，并说明用途和解除条件。
- 研究结论形成并完成适用审查后，由主会话组织、获分配的执行者在授权目录内完成证据整理与清理，再报告本轮收尾完成。停止或放弃一个方向也按实际状态收尾；异常现场及待核查证据先保留。已获授权范围内、本轮生成且符合清理条件的临时产物直接处理，不逐个文件重复请批；不据此清理业务仓库、历史研究、共享数据源、他人产物或归属不明对象。
- 保留足以复核结论和选择过程的最小证据集合：研究约定与审查结论、源码与产物身份、生效配置和命令、输入版本与用途、必要分析脚本、全部相关尝试的结果与成本，以及支撑关键主张、反证和异常定位所需的原始事实。失败、负面及未选中结果的必要记录不能删去，也不能只留胜出模型或一张汇总图。输入已有可靠保管位置时保留准确引用和读取条件，不重复复制整份数据；唯一必要证据不能以“以后可重跑”代替。
- 按实际用途保留采用模型的权重、变换与推理配置，以及约定恢复或复核所需状态。其余已无用途的检查点、重复导出、解压副本、临时分片、缓存和构建产物，在必要证据保存且引用有效后删除；保留所有尝试的记录不等于永久保留所有大文件。不设统一保留天数，不因文件名含 `tmp`、`cache` 或候选未胜出就认定可删。
- 在原研究 Issue 或收尾报告中写清保留内容及用途、有效证据入口、已清理对象、实际释放空间，以及遗留对象、原因、负责人和处理条件。未执行清理或未测得释放量时如实说明；研究结论与收尾状态分别报告，清理尚未完成时不能把本轮全部义务标为完成。父任务仍需的证据按其验收与保留约定处理，不随子轮次结束删除。

### GitHub 访问与账号

研究主会话仅在执行已授权且需要认证的 GitHub 访问前核验账号，并核对目标仓库。读取公共原则、安装或维护 Skill、仓库外分析不自动触发核验；子角色所需的平台事实由主会话交接，不自行核验账号。平台写入仍限于本轮获准维护的研究对象。

账号复用治理本机绑定中的 `github.controller.login` 与 `github.controller.config_dir`。绑定文件优先取非空 `CODEX_GOVERNANCE_CONFIG`，否则取 `${XDG_CONFIG_HOME:-$HOME/.config}/codex-governance/local.toml`。`config_dir` 必须是实际绝对路径，按字面值读取并按 shell 规则引用，不对值执行 shell 求值，也不展开其中的 `~` 或环境变量。不读取其指向目录内的认证材料正文；账号绑定和认证材料不写入公开记录。

使用内联 `GH_CONFIG_DIR=<绑定的 config_dir> gh api user --jq .login`，核对结果与绑定的 `login` 一致；后续 GitHub CLI 命令沿用同一内联绑定，不修改全局账号，也不把继承的 `GH_CONFIG_DIR` 当作身份事实。绑定缺失、目录不可用或实际账号不符时，停止受影响的平台操作并报告具体缺口，不猜测或切换其他账号。复用此绑定和核验方法不启用工程治理，不要求 Profile，也不授予代码交付权限。

## 方法参考

[Optiver 的 Research at Scale](https://www.optiver.com/insights/technology-blog/research-at-scale/)说明研究迭代与可复现计算基础设施的关系。本流程借鉴端到端成本和复现意识，不要求引入其平台。

[Bailey 与 López de Prado 的 Deflated Sharpe Ratio](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf)讨论多次选择对业绩判断的影响。本流程因此保留尝试和选择过程；不把某个 Sharpe 修正或样本阈值强制用于本项目的短窗数据。

[scikit-learn 的并行与资源管理说明](https://scikit-learn.org/stable/computing/parallelism.html#oversubscription-spawning-too-many-threads)说明作业并行与内部线程叠加可能增加调度开销。本流程据此核对总资源需求和实际吞吐，不要求使用该库或照搬其线程配置。
