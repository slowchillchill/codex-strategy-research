# 研究与工程交接

本文件用于研究中发现能力缺口、实现问题或必须改变公共行为的情况。研究按[共同研究流程](research-workflow.md)推进；工程任务遵守目标仓库适用规则。两者互相交接证据，不互相代替验收。

## 按实际行为判断归属

| 情况 | 研究侧如何处理 |
| --- | --- |
| 策略按合同运行，但亏损、拒绝、无成交或没有预期优势 | 作为经营事实检验假设；不能仅凭结果不理想申报程序故障 |
| 缺少回答具体问题的证据 | 先核对请求、反馈、成交、账本和已有报告；列明答不了的主张及最小补充，不默认建设通用诊断系统 |
| 本轮仓库外的派生分析脚本或报告计算错误 | 当前授权内自主修正并验证受影响结论；保存原事实与修正关系，不改写底层经济事实 |
| 业务仓库内任意文件有误，包括报告脚本、配置与文档 | 只读定位并向用户报告；修复很小也不由研究组修改 |
| 共享策略、训练核心、模拟、执行、账本或持久接口偏离明确合同 | 固定最小复现和影响范围，提交用户审查；不在消费者内复制或绕过公共能力 |
| 当前实现符合合同，但业务需要新能力或改变语义 | 作为研究发现提出具体选项、收益与成本；按现有授权边界取得决定后交工程 |
| 预期语义或错误原因仍不清楚 | 保留未知，只停止依赖该未知的判断或作业；先核对合同、原始证据与实现，不凭报错标签确定责任 |

源码、产物与平台记录权限以[共同研究流程第一节](research-workflow.md#1-研究对象与权威来源)为准。研究主会话及子角色都不能修业务仓库、创建 PR 或派生开发代理；改文件后缀、临时复制、动态替换或称为原型都不能绕过。现有正式接口支持的参数研究在原授权内进行，不自动产生开发任务。

## 最小问题反馈

在所属研究 Issue 中记录“待用户审查”的问题，并直接向用户汇报。提供足以让用户裁决、工程方复现和判断的材料，不另建状态系统：

1. **问题和业务影响**：预期行为、实际行为及其差异，指出依据来自哪个有效合同或已批准需求。
2. **准确现场**：代码、构建或模型身份，必要配置、输入与初始化，发生条件、原始错误和最小证据入口。
3. **当前判断**：已核实事实、待验证解释、无法回答的事项；区分实现错误、错误校验和业务假设失败。
4. **影响与可继续工作**：哪些候选、运行、报表或结论可能受影响，哪些独立工作仍可进行。无法界定时说明缺口，不直接宣布全部历史作废。
5. **建议与验证**：最小修复或补充方案，如何识别原错误，预计计算和维护成本，是否改变业务语义或投入。

研究组可准备完整开发 Issue 草稿，但不把草稿当已签发任务，不自行分配开发代理或开启工程流水线。用户审查后，由用户指定或授权的开发工作流建立、接手工程任务并双向关联研究入口。研究 Issue 维护对实验结论的影响；工程 Issue 维护修复、测试及代码交付，不复制两套合同。用户未签发前保留研究提案状态。

## 停止范围与工程返回

发现结果可能失真时，按当前合同停止受影响的采用结论和依赖计算，保留必要现场；更严格的任务停止要求优先。对原因不明的错误、实质困难和仓库外授权辅助分析的修复尝试，遵守公共工程准则的异常处理规则；该规则不授权修业务仓库，角色交接不能重置停止条件。普通经营亏损或假设被反证不属于程序异常，不启动“修到成功”的循环。

工程方返回用户签发入口、实际交付状态、准确源码与产物版本、变更语义、验证结果和已知限制。研究方据此判断证据是否仍适用：

| 修复影响 | 研究侧的后续判断 |
| --- | --- |
| 仅显示或派生分析错误，原始经济事实正确 | 更正派生报告及受影响结论，说明替代关系；不无依据重跑回放或训练 |
| 输入、初始化、规则、执行或账户计算错误 | 定位受影响运行和比较关系，旧结果保留原身份并标明可用范围；按授权补必要回放 |
| 特征、标签、奖励、训练环境或数据用途错误 | 同时核对训练产物和评价资格；不能仅重做报表就恢复旧模型结论，是否重训由实际影响决定 |
| 新增观察证据但未改变业务行为 | 核对实现确实只补证据及其运行成本；已有证据仍够用时不为日志完整而重跑 |
| 有意改变策略或公共业务语义 | 建立新候选或新规则身份，重新说明可比边界；不能把旧成绩改名继承 |

工程测试通过只证明所验证的实现要求。恢复研究还需满足当前研究的输入资格、准确版本、剩余预算与授权；交付不自动批准重跑或重训，原授权仍明确适用时也不重复请批。研究证据支持某策略，不授予研究组代码交付、部署、PAPER、LIVE 或真实资金操作权限。

## 目标项目适配

在 `btc-updown-marketmaker` 中，按 [#1](https://github.com/slowchillchill/btc-updown-marketmaker/issues/1) 的模块归属与交接顺序，把问题交回实际责任模块；A 的经营要求回读 [#185](https://github.com/slowchillchill/btc-updown-marketmaker/issues/185) 及所属任务（例如 [#315](https://github.com/slowchillchill/btc-updown-marketmaker/issues/315)），B 回读 [#181](https://github.com/slowchillchill/btc-updown-marketmaker/issues/181)。改变业务语义、实质验收或工程取舍时核对 [#62](https://github.com/slowchillchill/btc-updown-marketmaker/issues/62) 的相关原始决定，普通执行记录不因此新建裁决。

本交接流程是本项目的研究与工程分工，不声称复制任何机构未公开的内部审批制度。
