# 研究与工程交接

本文件用于研究中发现能力缺口、实现问题或必须改变公共行为的情况。研究按[共同研究流程](research-workflow.md)推进；工程任务遵守目标仓库适用规则。两者互相交接证据，不互相代替验收。

## 按实际行为判断归属

| 情况 | 研究侧如何处理 |
| --- | --- |
| 策略按合同运行，但亏损、拒绝、无成交或没有预期优势 | 作为经营事实检验假设；不能仅凭结果不理想申报程序故障 |
| 缺少回答具体问题的证据 | 先核对项目已有原始事实、输入输出、反馈和报告（交易项目适用时包括成交与账本）；列明答不了的主张及最小补充，不默认建设通用诊断系统 |
| 本轮仓库外的派生分析脚本或报告计算错误 | 当前授权内自主修正并验证受影响结论；保存原事实与修正关系，不改写底层经济事实 |
| 业务仓库内任意文件有误，包括报告脚本、配置与文档 | 只读定位；授权内必要依赖直接签发开发组，超出授权交用户；修复很小也不由研究组修改 |
| 共享策略、训练核心、模拟、执行、账本或持久接口偏离明确合同 | 固定最小复现和影响范围，按授权直接签发开发组；不在消费者内复制或绕过公共能力 |
| 当前实现符合合同，但业务需要新能力或改变语义 | 作为研究发现提出具体选项、收益与成本；按现有授权边界取得决定后交工程 |
| 预期语义或错误原因仍不清楚 | 保留未知，只停止依赖该未知的判断或作业；先核对合同、原始证据与实现，不凭报错标签确定责任 |

源码、产物与平台记录权限以[共同研究流程第一节](research-workflow.md#1-研究对象与权威来源)为准。研究主会话及子角色都不能修业务源码或自行转开发角色；主会话可为自己签发的已推送开发分支创建 PR，技术维护、审查和合并归开发组；改文件后缀、临时复制、动态替换或称为原型都不能绕过。现有正式接口支持的参数研究在原授权内进行，不自动产生开发任务。

## 最小问题反馈

在所属研究 Issue 保留问题和影响，再在准确工程 Issue 签发独立工程依赖，关联原研究入口。提供足以让工程方复现和判断的材料；需要改变授权或合同的部分标为待用户批准，不另建状态系统：

1. **问题和业务影响**：预期行为、实际行为及其差异，指出依据来自哪个有效合同或已批准需求。
2. **准确现场**：代码、构建或模型身份，必要配置、输入与初始化，发生条件、原始错误和最小证据入口。
3. **当前判断**：已核实事实、待验证解释、无法回答的事项；区分实现错误、错误校验和业务假设失败。
4. **影响与可继续工作**：哪些候选、运行、报表或结论可能受影响，哪些独立工作仍可进行。无法界定时说明缺口，不直接宣布全部历史作废。
5. **建议与验证**：最小修复或补充方案，如何识别原错误，预计计算和维护成本，是否改变业务语义或投入。

研究主会话可在当前授权内直接签发必要工程依赖，不经过逐项前置决策审批。准确 Issue 写明研究组来源、范围、非目标、验收、预计成本、同一阶段预算归属、累计消耗和剩余额度、原授权及停止条件。依赖计入同一阶段预算，不能另复制额度。超出范围、预算、数据用途或原合同保留事项时，先交用户批准。

通过共同协作规则的单一适配器向准确开发参与者发送工程 Issue。跨环境在 GitHub 来源任务评论交接，由接收方在自己的环境核对现场并显式加载 Skill；可访问的 Agent Center 使用结构化 Skill 输入或向原活动轮次传消息。开发组用自己的固定身份接单、规划、实现、验证和推送，再将仓库、基线、分支、完整提交及 PR 材料直接交回研究组。研究主会话先查询同头分支 PR，不存在时以研究身份创建，再回传链接；不改业务代码、不代替技术审查。开发组维护、独立正式 Review、普通合并并收尾后，结果固定回准确研究参与者。

跨路线公共缺口先检查原模块和既有准确任务，明确单项主责路线、受影响消费者及预算。原跨路线请求和实际工程签发分别留来源与返回入口；工程按实际签发组创建 PR 并返回，再由接收路线沿原请求回传。公共工程默认计入请求方阶段预算，消费路线的适配计入自己的预算；共同出资须有明确授权，同一成本只计一次。公共 PR 合并、研究能力可用及每条路线实际采用分别判断，不重复实现相同能力，不因公共记录整理而改变签发归属。

研究 Issue 维护证据及结论影响，工程 Issue 维护实现与交付，预算及合同用链接引用。来源 Issue 正文由明确维护者更新，其他参与者以评论提供请求和证据；公共记录维护不增加裁决权。任务来源不改变开发身份；决策组监督不改写原签发组。恢复前核对未提交现场、活动作业、原写入者、遗留队列和剩余预算；远端现场由实际执行方确认，沉默不表示接受或停止，未确认停止不启动第二执行者。

## 停止范围与工程返回

发现结果可能失真时，按当前合同停止受影响的采用结论和依赖计算，保留必要现场；更严格的任务停止要求优先。对原因不明的错误、实质困难和仓库外授权辅助分析的修复尝试，遵守公共工程准则的异常处理规则；该规则不授权修业务仓库，角色交接不能重置停止条件。普通经营亏损或假设被反证不属于程序异常，不启动“修到成功”的循环。

工程方返回原研究签发入口、实际交付状态、准确源码与产物版本、变更语义、验证结果和已知限制。研究方据此判断证据是否仍适用：

| 修复影响 | 研究侧的后续判断 |
| --- | --- |
| 仅显示或派生分析错误，原始经济事实正确 | 更正派生报告及受影响结论，说明替代关系；不无依据重跑回放或训练 |
| 输入、初始化、规则、执行或账户计算错误 | 定位受影响运行和比较关系，旧结果保留原身份并标明可用范围；按授权补必要回放 |
| 特征、标签、奖励、训练环境或数据用途错误 | 同时核对训练产物和评价资格；不能仅重做报表就恢复旧模型结论，是否重训由实际影响决定 |
| 新增观察证据但未改变业务行为 | 核对实现确实只补证据及其运行成本；已有证据仍够用时不为日志完整而重跑 |
| 有意改变策略或公共业务语义 | 建立新候选或新规则身份，重新说明可比边界；不能把旧成绩改名继承 |

工程测试通过只证明所验证的实现要求。恢复研究还需满足当前研究的输入资格、准确版本、剩余预算与授权；交付不自动批准重跑或重训，原授权仍明确适用时也不重复请批。研究证据支持某方案，不授予研究组代码修改、技术审查、合并、部署或真实资金操作权限。

## 目标项目适配

在 `btc-updown-marketmaker` 中，从[项目参考的合同入口](projects/polymarket.md)读取总体合同，按其模块归属与交接顺序把问题交回实际责任模块；A 的经营要求回读 A 策略业务合同及当前所属研究任务，B 回读 B 当前训练合同。改变业务语义、实质验收或工程取舍时核对裁决索引中的相关原始决定，普通执行记录不因此新建裁决。

本交接流程适用于已接受有效委托的项目，不声称复制任何机构未公开的内部审批制度。
